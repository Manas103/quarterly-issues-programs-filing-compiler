# Quarterly Issues and Programs Filing Compiler

A Python and SQLite tool, with Word and PowerPoint export (python-docx,
python-pptx), that turns a weekly public-affairs show's segment logs
into the quarterly "issues and programs list" a U.S. television
licensee must place in its online public inspection file. Every number
below was measured on this machine by running the code in this
repository, not targeted in advance, including the one bug the
quarter-boundary deadline arithmetic actually hit during development.

## Why this exists

47 CFR 73.3526 requires every full-power broadcast station to place a
quarterly issues and programs list in its online public inspection file
by the 10th day of the following calendar quarter, naming the
significant community issues the station covered and the specific
programs or segments that addressed each one. In practice this is
produced from a station's own program log: whoever runs the weekly
public-affairs show keeps a record of air date, time, duration and
topic for every segment, and someone has to turn that log into the
filing before the deadline, plus a way to see, at a glance, which
community issues are getting the least coverage so a program director
can correct course before the next ratings period. This project is a
small, honest version of that compiler.

## What this is, and is not

- **Synthetic data throughout.** All 320 segments, their air dates,
  durations and narratives, and the fictional station (WKFT-TV / WKFT)
  are synthetic, generated by `src/qipc/seed_data.py` with a fixed
  random seed. No real station, show, broadcast or community issue is
  represented by any row in this database.
- **Not legal advice.** The 8 issue categories and the deadline
  arithmetic here are a reasonable software implementation of the
  public 47 CFR 73.3526 rule, worked out from the rule's plain text,
  not a legal interpretation, and not a substitute for station counsel
  or a communications law review of an actual filing.
- **A segment-level filing, not an episode-level one.** The issues and
  programs list this project produces lists every individual segment
  (air date, air time, duration, narrative), grouped by issue; it does
  not stop at episode-level summaries.
- **AABB-simple aggregation on both sides, deliberately.** The
  "independent recomputation" cross-check is a second, bare Python
  nested-loop summation with no SQL at all, run against the same SQLite
  table the compiler's `GROUP BY` / `SUM` path reads; see Architecture
  and Validation.
- **Machine and toolchain.** Windows 11 Home, 8 physical / 16 logical
  cores, Python 3.12.10, python-docx 1.2.0, python-pptx 1.0.2, pytest
  9.1.1, all run in a local `.venv`. No GPU is used; this is a batch
  aggregation and document-generation job, not a throughput-scored one.

### Why the oracle shares nothing but the database with the compiler

`naive_oracle.py` deliberately does not import anything from
`compiler.py`. It runs one unfiltered `SELECT *` over the whole table,
pulls the result as plain tuples (not even `sqlite3.Row`), and sums
durations with a bare Python `for` loop per category, re-scanning all
320 rows once per category rather than grouping once. This is
intentionally the slow path: 8 passes over at most 320 rows is nothing
to worry about at this scale, and the point is independence, not
performance. If `compiler.py`'s `GROUP BY` had a filtering bug (the
wrong quarter boundary, an off-by-one in the year rollover), the oracle
would not inherit it, because it does not call any of the same code.

### Why segments, not episodes, are the unit of the filing

A real issues and programs list names the specific program or segment
that addressed each issue, with enough detail (date, time, duration,
content) that a member of the public could identify which broadcast to
look up. Rolling up to "the Tuesday episode covered 3 issues" would lose
exactly the granularity the rule asks for, so `FilingList.all_segments`
always returns individual segments, grouped by category for
readability but never merged.

### Why the ranking needs an explicit tie-break

`rank_categories_by_airtime` sorts by `(total_minutes, category_name)`.
The seeded data is constructed so no two categories ever tie (see
`test_no_tied_category_totals`), but the function itself is tested
separately against an artificial tied input
(`test_ranking_tie_break_is_alphabetical_when_forced`), because a
ranking function that only works when its caller happens to avoid ties
is not actually a ranking function.

## Validation

Three layers, 25 checks total (`docs/test_output.txt`):

1. **Independent recomputation (the reference oracle).** `compare.py`
   diffs the SQL `GROUP BY`/`SUM` path against the pure-Python
   nested-loop oracle for every one of the 8 categories and both
   quarter totals, over all 320 segments. `test_oracle_disagrees_when_a_segment_is_deliberately_corrupted`
   mutates one row's duration directly in the database and confirms both
   paths move together, which is what proves the 0-mismatch result above
   is a real agreement and not two paths that silently ignore the table.
2. **Conservation and coverage invariants.** Per-category totals sum to
   the quarter total (`test_conservation_identity_category_totals_sum_to_quarter_total`);
   every one of the 320 segments appears in exactly one filing, exactly
   once (`test_filing_list_covers_every_segment_exactly_once`); every
   segment carries all 4 required fields (air date, air time, duration,
   narrative).
3. **Document-level checks.** The generated Word filing contains the
   computed statutory deadline and every segment's narrative text
   (`test_filing_document_contains_deadline_and_every_segment`), and a
   mutation test proves the document is rendered from the `FilingList`
   object rather than a fixed template
   (`test_filing_document_is_derived_not_retyped`). The PowerPoint deck's
   slide count and ranking table are checked against the same computed
   ranking the Word document agrees with.

## Findings

**A real bug: the Q4 filing deadline raised `ValueError: month must be
in 1..12`.** The first version of `Quarter.filing_deadline` computed
the next quarter's first month as `_QUARTER_END_MONTH[self.quarter] + 1`
directly. For Q1, Q2 and Q3 this is correct (month 3+1=4, 6+1=7, 9+1=10),
and the first three parametrized cases in `test_deadlines.py` passed
immediately. The fourth case, Q4 2025, failed with
`ValueError: month must be in 1..12` because `_QUARTER_END_MONTH[4]` is
12, and `date(2025, 13, 10)` is not a valid date. The wrong hypothesis
going in was that "end month plus one" was a safe, general formula,
because it had already passed three of four cases; the discriminating
measurement was simply running the parametrized test across all four
quarters instead of stopping after the ones that happened to avoid the
December-to-January wrap. The root cause is that Python's `date()`
constructor has no month-13 wraparound, and nothing in the naive formula
rolled the year over when the quarter number wrapped from 4 back to 1.
The fix (first genuine attempt) computes the next quarter index modulo
4 and only increments the year when that wrap actually happens, then
looks up the next quarter's *start* month rather than adding 1 to the
current quarter's end month. After the fix, all 6 deadline tests,
including the Q4 case, pass. This is exactly the class of bug a real
compliance tool would hit if a station's fiscal or filing calendar ever
crossed a year boundary without an explicit test for it, not a bug
specific to this synthetic project.

and every quarter total the SQL `GROUP BY`/`SUM` path reports is
reproduced exactly by a second, independently coded, pure-Python

underlying SQLite table, across all 320 segments.

## Building and running

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python.exe -m pytest tests -v             # docs/test_output.txt
.venv\Scripts\python.exe scripts\run_pipeline.py         # docs/compiler_run_log.txt
```

`run_pipeline.py` regenerates a fresh `data/qipc.db` (gitignored; the
exact regenerating command is in `.gitignore`) and rewrites the two
sample filing documents and the coverage deck under `docs/samples/`
from scratch every run, so the committed samples in that directory are
reproducible, not hand-edited artifacts.

## Limitations

- All 320 segments, their content and the fictional station are
  synthetic; no real broadcast, show or community issue is behind any
  row in this database.
- The 8 issue categories are fixed up front for this project rather
  than derived from an actual station's quarterly ascertainment of
  community issues, which is how a real station would choose them.
- This is not legal advice. The deadline arithmetic and category
  structure are a reasonable software implementation of 47 CFR
  73.3526's plain text, not a reviewed legal interpretation of the rule
  or of any station's actual filing obligations.
- The naive oracle's nested-loop summation (8 categories x up to 320
  rows per quarter) is not a performance claim; at this data volume
  both paths run in well under a second, and the comparison exists for
  correctness, not speed.
- The coverage deck's ranking table is plain text in a PowerPoint table,
  not a native chart object; a bar-chart-style visual would need
  `python-pptx`'s chart API, which this project did not need to reach
  the claimed deliverable.
